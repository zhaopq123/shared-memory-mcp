# 设计取舍：为什么是「文件 + git + 队列」

这份文档解释**为什么不用另外几种显而易见的做法**。如果你正打算改这套设计，先读这里。

---

## 一、为什么存储是 Markdown 文件，不是数据库

候选做法：SQLite / Postgres / 向量库。

**选文件的理由：**

1. **故障时的可抢救性。** 数据库文件损坏时，你需要工具才能读出内容；Markdown 坏了用 `cat` 也能看。记忆是长期资产，优先级高于查询性能。
2. **人能直接参与。** 手改、`grep`、拖进编辑器 —— 这些都免费获得。数据库做不到。
3. **git 免费提供版本化。** 一个目录天然能 `git init`；数据库要额外做备份策略。
4. **迁移成本接近零。** 换个服务、换个机器，拷贝目录即可。

**代价与取舍：**

- 检索是全量内存过滤。当前实现适合几千条量级。
  **超过这个量级要建索引** —— 那时应该加一层，而不是换掉存储层。
- 并发写靠队列而不是数据库事务。这是刻意的：队列的语义更简单，也更容易验证（见下）。

---

## 二、为什么用队列，不用锁

候选做法：`flock` 文件锁 / 数据库行锁 / 分布式锁。

**核心论点：需求是「不隔离」，那并发写就是必然的，问题只是怎么让它安全。**

| 做法 | 问题 |
|---|---|
| 文件锁 | 要处理「持锁进程卡住但没死」；锁文件本身是垃圾 |
| 数据库行锁 | 引入一个数据库服务；记忆量级不需要 |
| Redis 分布式锁 | **要设 TTL，否则永久死锁** —— 多一个失败点 |
| **FIFO 队列** | **没有上述问题** —— 排队天然不覆盖、不死锁 |

队列的额外好处是**可观测**：`memory_stats` 能报积压深度，一眼看出是不是堵了。
锁做不到这一点（你只能知道「有人在持有」，不知道排了多少）。

### 最容易踩的坑：ack 必须在落盘之后

```python
# ❌ 错：入队就返回成功
async def submit(self, fn):
    await self._queue.put(fn)
    return {"ok": True}

# ✅ 对：等真正完成
async def submit(self, fn):
    fut = loop.create_future()
    await self._queue.put((fn, fut))
    return await fut
```

**为什么这个错误很危险：** 进程一崩，排队中的请求全丢，但 agent 已经收到
「写入成功」并基于这个假事实继续工作 —— 而内容根本不存在。
错误会以「记忆莫名其妙丢失」的形式出现在很远的地方。

### 第二个坑：容量要数「在办」，不只是「排队」

```python
# ❌ 错：只数排队中的
if self._queue.qsize() >= self._max_depth:
    raise QUEUE_FULL

# ✅ 对：包含正在执行的那个
if self._outstanding >= self._max_depth:
    raise QUEUE_FULL
```

写者 `get()` 之后队列长度立刻减一，但那个任务还在跑。
只数 `qsize()` 会让「1 个在办 + max_depth 个排队」被算成「未满」——
于是超额任务不是被拒绝，而是**无限等待**。

这个 bug 在实测中表现为：**第三个并发写永远不返回**。
承诺的「队列满明确拒绝」被悄悄变成了「静默挂起」。

## 三、为什么读不进队列

读不改状态，没有竞争。让读也排队的话，「一个 agent 在写」会变成
**「所有 agent 都卡住」** —— 那比数据竞争更糟，因为它把局部问题放大成全局故障。

所以：**写串行，读并发。**

---

## 四、为什么不用 embedding / 向量检索

引入 embedding 等于引入四个额外失败点：

1. **API key** —— 要管理、会过期、会泄漏
2. **网络依赖** —— 断网就检索不了（而记忆在本地）
3. **额度限制** —— 用超了要么报错要么扣钱
4. **模型行为** —— 换模型、改了 prompt，排序就变了

换来的收益是语义召回（「部署」能召回「上线」）。

**在本项目的定位下这不划算** —— 记忆条目通常标题清晰、标签规范，
子串匹配 + 标签过滤已经够用。而且**结果可复现**：
同样的库和查询永远给出同样的排序，这对调试和信任都很重要。

真需要语义搜索时，正确的做法是**加一层可选索引**，而不是把 embedding
塞进存储路径。

## 五、为什么面板是只读的

写入路径上有三道保护：

1. 队列串行（防并发覆盖）
2. git 提交（防丢失、可回滚）
3. 软删除（防误删）

**在面板上开写入口等于绕过这三道。** 而且面板是给人用的 —— 人不需要
高频写入，agent 才需要。让写入只有一条路径，就只有一个地方需要保证正确性。

## 六、为什么工具控制在 14 个（v1 时是 6 个）

有实测结论指出：**工具数量每增加一个，agent 选对工具的概率都会下降。**

所以按「一个动词一个工具」划分，而不是「一个粒度一个工具」
（不做 `memory_write_short` / `memory_write_long` 这种）。

数量演进全部经过这道闸：

- **v1：6 个**（search/get/write/list/delete/stats）
- **多租户：+2**（whoami / libs）—— 没有它们，agent 不知道自己是誰、
  能看哪些库，后续每个操作都在猜
- **优化期：+2**（export / import）—— 导入导出是**新动词**，
  没法塞进既有工具的语义里

其余新能力（claim / status / 时效参数 / with_commits / include_superseded）
全部是**可选参数**，不是新工具。参数多的代价由工具描述承担，
工具多的代价由 agent 的选择正确率承担 —— 前者便宜得多。

`memory_search` 是唯一被期望高频调用的 —— 它的工具描述里写死了
「开工前先调这个」，因为 **MCP 只提供工具，不会自动被调用**。
召回层的抓手只能是工具描述本身。

## 七、为什么身份来自凭据，不来自参数

候选做法：工具签名里收 `user_name` / `libs=[...]` / `scope=company`。

**全部拒绝，理由是同一个：工具的参数 schema 是暴露给客户端的。**
客户端能填的参数，就是客户端能伪造的面。

```
工具签名(user_name)      → 客户端可以冒充任何人
工具签名(libs=[...])     → 客户端可以越权读列表
工具签名(scope=company)  → 同上
```

正解是 **contextvar**：鉴权中间件（ASGI 最外层）校验 Bearer token 后
`set_identity(user)`，工具层 `require_user()` 取。工具签名里根本没有
身份参数，「伪造身份越权」在结构上就不可能。

连带两个设计：

- **`lib` 参数只能收窄不能扩大** —— 在你有权限的集合里选一个；
  传没权限的库返回 403 而不是内容。
- **不传 `lib` 的写落个人库** —— 写是最容易污染别人的操作，
  默认最小污染面。要往共享库写必须显式指定，且过写权限检查。

## 八、为什么是公司/小组/个人三级库

候选做法：全库一个池子（v1）或每 agent 一个桶（mem0 型）。

- **一个池子**的问题：公司规范和某个人的草稿混在一起，没有边界，
  误改公司口径和误改同事笔记同样容易。
- **每 agent 一个桶**的问题：那正是本项目要解决的反面 ——
  结论互相不可见，重复踩坑。

三级库是这两个极端之间的务实解：

| 库 | 归属 | 读 | 写 |
|---|---|---|---|
| company | 公司 | 全员 | 仅 admin（默认）|
| group-xxx | 小组 | 组员 | 组员 |
| user-xxx | 个人 | **仅本人（admin 也不行）** | 本人 |

个人库对 admin 也不开放是刻意的 —— 个人库的意义就是私密；
要共享应该显式写进组库或公司库，那个动作本身就是一次确认。

## 九、防污染四道闸（共享记忆的真正风险）

丢数据有 git 兜底，**脏数据被当成事实传下去**才是这个系统最大的风险。
四道闸按"写入时 → 读取时 → 会话开始时"分布：

**① claim 三分（写入时标注，读取时过滤）**
`fact` / `inference` / `proposal`。这是反幻觉的结构性落点：
问"现行口径"时 `claim=fact` 过滤，看到 `inference` 天然多一个心眼。
服务端按规则推断兜底（不填也有值），但**显式标注优先**。

**② 时效四态（取代而非删除）**
`superseded-by` / `valid-until` / `review-after`。旧口径标记后
退出现行口径但原文保留 —— 删掉旧记忆等于让后人重走死路。
`status=active` 因此是 search 的默认（老部署改配置可恢复旧行为）。

**③ 写时防重五层**
upsert 标题去重 / create 报 CONFLICT / append 保留原文 /
`ok` 与 `committed` 分家（v2：`ok=true` 即已落盘，`committed` 只说进没进
版本库 —— 防 agent 把"没提交"当失败而重试出重复）/
撞名加 id 后缀。外加**写时关联提示**：写入响应带 top3 相似既有记忆，
"先拉再推"不强制（决策：强制会拖慢每一笔写），但服务端把"拉"的
时机还给你。

**④ 启动变更摘要**
initialize 中间件把「你离开期间的变更」追加进 instructions。
见第十二节。

## 十、为什么导入导出是字节级，不是重新序列化

候选做法：导出时把 frontmatter + body 重新渲染一遍。

**拒绝：渲染即失真。** 重新序列化会丢字段顺序、丢空白、丢注释，
而「导出→导入→再导出」无损往返是这条链路唯一可验证的正确性标准。

做法：`shutil.copy2` 字节级拷贝 + `manifest.json` 记每条的 sha256。
导入时逐条校验，对不上就跳过并报错。**刻意不走 `apply_rules_on_write`**
（不自动推断、不补全）—— 导入的价值就是原样还原。

冲突策略按**标题**判定（与写时防重同一把尺子）：
`skip`（默认，共享库里"不覆盖"是默认道德）/ `update` /
`rename`。`workspace` 是**过滤器不是改写器**：只导目标项目的条目，
不改写条目内容。

安全：路径白名单与 `_slug` 同口径（2026-10-13 修正：第一版正则
`[\w.-]` 不含中文标点，标题带 `·` 的条目被静默跳过）+
resolve 双重防穿越 + schema 版本不匹配直接拒绝。

## 十一、为什么 stats 默认不带 git 历史

实测每次 `git log` fork 子进程约 60ms（与数据量无关的固定开销），
而 stats 的核心用途（队列积压、条数、dirty 状态）不依赖它。
默认 `with_commits=False` → stats 从 ~0.35s 降到 ~0.1s 量级；
面板/排查场景显式传 `true`。**默认值服务稳态，显式参数服务排查。**

## 十二、digest 为什么用中间件 + seen 记账

**需求**：会话开始时告诉 agent「你不在时发生了什么」——
否则它要么冷启动盲写，要么拿着过期口径干活。

**为什么是 `on_initialize` 中间件**（而不是一个 `memory_digest` 工具）：
MCP 的 initialize 响应有 `instructions` 字段，客户端会并进系统提示。
挂在这个点上，摘要是**推**的；做成工具，摘要是**拉**的 ——
而"忘了拉"正是要解决的问题。fastmcp 4.1.0 有 `on_initialize` 钩子，
正路可行就不退化。

**为什么需要 seen 记账**：note 的 `updated` 是秒级精度，光靠
`updated >= since` 无法区分「游标建立前一刻写入的基线条目」和
「游标建立后同秒写入的新条目」—— 前者重复播报，后者可能漏报。
时间精度不够就记账：播报过的 note id 进 seen。代价是游标文件变大
（有 1000 条上限），换来**精确一次**。

**三条纪律**：零变更不播报（稳态零 token）；任何失败静默
（digest 挂掉不能影响 initialize）；长期告警态但无人动过的条目
不重复播报（那是 `memory_view(kind="expiring")` 的职责）。
